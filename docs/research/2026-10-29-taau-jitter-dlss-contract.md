# TAAU 的 SubPixelJitter → DLSS：契约、单位与判别实验

## 0. 范围与证据

问题：把引擎 TAAU 的亚像素 jitter 喂给 DLSS-SR 时，**要不要做变换**？不改（或改错）会看到什么？
本文只回答这一件事，不重复 TAAU 的其它算法（那份在 `2026-10-28-taau-decompiled.md`）。

三路证据，互相独立：

1. **TAAU pixel shader**（SM6.3 DXIL，SHA-256 `b6e91d619ee2…`；SM5.0 DXBC `757cd3c5b236…` 逐段一致）。
   直接读常量缓冲与坐标运算，不拟合。反汇编副本在 `_local/scratch/upscaling/`（不进 git）。
2. **Mac 1.26.32 全符号库**：找到 jitter 常量表本体，并用运行时 ctx dump 把「索引 → 表项 → 喂给
   shader 的值」逐帧对上。地址与签名记在 canon `taau_jitter_table`（本文不抄地址）。
3. **RTXPT 的 DLSS 参考实现**（`D:\Documents\RTXPT`，v1.9.0）：DLSS 侧同名量的产生与传参方式。

分级：第 2 节的表与索引、第 3 节的坐标契约、第 4 节的 DLSS 侧用法均为**已确认**；
第 4 节末尾「NGX 直连与 Streamline 等价」是**假设**；第 6 节「世界帧到底有没有按这个偏移渲染」
是**未解决**，判据见 §7。

## 1. 一句话

> 这个 jitter **不需要任何数值变换**：它就是 Halton(2,3)−0.5 在 [−0.5, +0.5]、单位是**渲染分辨率像素**、
> 屏幕 y 向下的亚像素偏移，与 DLSS 的 `Jitter.Offset.X/Y` 同一个空间。

所以「直传会抖」不是少了一步换算，而是这个值没描述我们喂给 DLSS 的那一帧（§6）。

## 2. 这个值到底是什么（已确认）

引擎用的是**一张 16 项 float2 常量表**，`table[k]` 与 Halton 完全相等：

```
table[k] = float2(VanDerCorput(2, k+1), VanDerCorput(3, k+1)) - 0.5      k = 0..15
```

前几项：`(0, −1/6)`、`(−0.25, +1/6)`、`(+0.25, −7/18)`、`(−0.375, −1/18)`、`(+0.125, +5/18)`、
`(−0.125, −5/18)`、`(+0.375, +1/18)`、`(−0.4375, +7/18)` … 最后一项 `(−0.46875, +5/54)`。

与 RTXPT 的关系：`Rtxpt/Sample.cpp` 的 `TemporalAntiAliasingJitter::Halton` 分支是
`float2{ VanDerCorput(2, index), VanDerCorput(3, index) } - 0.5f`，`index = frame % phaseCount + 1`。
两者是**同一个序列**，只差相位数量（引擎 16、RTXPT 取 `max(32, 8×面积比)`）。

运行时核对（EXP-0047 的 `ctxs` 批次，连续四帧）：

| 帧 | `mCurrentJitterIdx` | ctx `+0x1e4/+0x1e8` | 表项 |
|---|---|---|---|
| #0 | 3 | (−0.375, −0.05556) | `table[3]` |
| #1 | 4 | (+0.125, +0.27778) | `table[4]` |
| #2 | 5 | (−0.125, −0.27778) | `table[5]` |
| #3 | 6 | (+0.375, +0.05556) | `table[6]` |

⇒ **索引是 0 基，每帧 +1，在 16 项上回绕**。

**更正**：`2026-10-24-vv-path.md` 与 `docs/specs/vv.md` 里「每帧递增回绕（2,6,10,14,…）」是
300 帧日志步长造成的采样假象，不是 +4。旧结论已进 `canon/refuted.jsonl`。

## 3. 单位与坐标：渲染像素、y 向下（已确认）

TAAU PS 的相关运算（DXIL 逐条）：

```
displayCenter = floor(uv * DisplayResolution) + 0.5
srcPos        = displayCenter * ratio - jitter - 0.5          // ratio = render/display
renderPixel   = round_ne(srcPos)                              // TextureLoad 的整数索引
```

`displayCenter * ratio` 已经是**渲染像素**坐标，jitter 从它里面被**直接减掉**，中间没有乘除任何分辨率。
所以 jitter 的单位就是渲染像素；`−0.5` 只是「像素中心 ↔ 整数索引」的约定，**不属于 jitter**。
y 方向：PS 里 MV 需要先 `mv.y = -mv.y` 才和它同一坐标系，jitter 不需要翻 ⇒ **jitter 是 y 向下**。

同一份 shader 还用 `delta = srcPos - round_ne(srcPos)` 算 `spatialWeight`（混合权重随亚像素不利位置
降到 0.05），说明「当前帧按某个亚像素偏移渲染」是这份 TAAU 自身的设计前提——不管那个偏移是不是
真的生效（见 §6）。

## 4. DLSS 侧要的也是这个量（已确认 + 一处假设）

RTXPT 是可直接对照的实现：

- `Rtxpt/Sample.cpp`：`float2 jitterOffset = m_view->GetPixelOffset();  // what UpdateViews applied this frame`
  → 原样塞进 `slConstants.jitterOffset`，**没有**乘分辨率、没有加减 0.5、没有翻 Y。
- 同一个 `GetPixelOffset()` 只在喂**光线相机**时才乘 `(1,−1)`
  （`Rtxpt/Shaders/PathTracer/PathTracerShared.h`：`data.Jitter = jitter * float2(1, -1);`），
  那是因为光线生成在 NDC、y 向上，不是 DLSS 的要求。
- 同一份 `View` 出来的 MV 也是像素单位：`mvecScale = {1/renderSize.x, 1/renderSize.y}`，
  注释写明 `donut has mvec in pixel space`。**jitter 与 MV 同空间，两者都不翻 Y。**

我们并不走 Streamline，而是直接调 NGX 的 `Jitter.Offset.X/Y`。**假设**：NGX 这两个参数与
Streamline 的 `jitterOffset` 同约定（Streamline 只是把 `slConstants` 翻成 NGX 参数）。这一条
没有本地证据，用 §7 的 `−j(n)` 实验可以顺带把它验掉（符号反了会立刻表现为幅度翻倍而不是消失）。

## 5. 因此不该做的变换

| 想做的 | 为什么错 |
|---|---|
| `× ratio`（当前 0.66） | 它本来就是渲染像素；乘了等于把它当显示像素 |
| `× 0.5` / `× renderSize` | 那是把像素当 UV / NDC；只有 ±0.25 量级的归一化值才这么干 |
| `+0.5` / `−0.5` | 与 §3 里那个像素中心的 `−0.5` 混了 |
| 跟着 MV 一起翻 Y | MV 需要 `(−z,+w)`（翻 Y **加上**时间方向取反，见 §3 与 `VvSr.cpp` 的 prep），jitter 两项都不需要 |
| 重排/降采样 | prep 是 `Load(int3(id.xy,0))` 的 1:1 拷贝，相位不变；一旦中间做了任何重采样，jitter 语义立刻失效 |

`src/neurodragon/vv/VvSr.cpp` 现在（TEST 开关打开时）就是原样传，数值层面没有缺变换。

## 6. 那为什么会抖：三个候选（2026-10-29 已定案为候选 1，见 §11）

原样传只在「色/深/MV 都是用这个偏移光栅化出来的」这个前提下成立。EXP-0098 的 A/B
（引擎值抖、置零稳）否掉的是这个前提，但它本身分不清三种情况：

1. **世界帧没有按它渲染**（或只有一部分 pass 按它渲染）⇒ 任何非零值都会注入一个假相位，只能喂 0。
2. **符号/轴向反了**（含 §4 那条假设不成立）⇒ 残差 ≈ 2×jitter。
3. **相位差一帧**：ctx 里的 jitter 比渲染那一帧早（或晚）一帧 ⇒ 残差 ≈ Δjitter，看起来就是"有点抖"。

量级上可以排除「尺度错」：若只是显示像素 vs 渲染像素的错，残差上限 0.17 px（真值是 `0.66×jitter` 时）
到 0.25 px（我们把 `1.5×jitter` 传进去时），属轻微 shimmer；用户描述的抖更像整份 jitter 量级的错位。

另有一个放大器：depth 语义（`near/(1−d)` 与 `DepthInverted=1`）尚未收口。depth 偏了，DLSS 的重投影
本来就在近似，此时再给它一个非零 jitter，亚像素错位就从"看不见"变成"看得见"。**重新打开 jitter 之前
应该先把 depth 定下来。**

## 7. 判别实验（每个都是改几行 + 面板切换，不需要新测量工具）

记 `j(n)` 为当帧 ctx 里的 jitter，`−j(n)` 为取负，`j(n−1)` 为上一帧的。

| 喂给 DLSS | 若「帧没按它渲染」 | 若「帧有、符号正确」 | 若「帧有、符号反」 |
|---|---|---|---|
| `j(n)`（现状） | 抖 | 稳（不应抖） | 抖 |
| `−j(n)` | 幅度**几乎不变** | 幅度**翻倍** | 稳 |
| `j(n−1)` | 抖 | 抖 | 抖；但若**稳** ⇒ 相位差一帧 |

判读：

- `−j(n)` 幅度翻倍 ⇒ 值与帧对得上，问题在别处（相位 / depth / MV 一致性），**不要**再去改符号或缩放。
- `−j(n)` 幅度不变 ⇒ 这一帧确实没按它渲染 ⇒ **只能喂 0**，并把"为什么 TAAU 自己也用这个值"单列。
  此时若还想拿到亚像素采样增益，就必须在渲染侧自己施加 jitter（另一个工程），不是喂参问题。
- `j(n−1)` 稳 ⇒ 引擎 ctx 的 jitter 领先渲染一帧，属于相位 bug，修 source。

更重但一次到位的做法：静止相机连拍 8 帧，dump 渲染分辨率的 `arg9` 与逐帧 jitter（`[vvsr] sr dump …
jitter=` 已有），离线拟合帧间亚像素位移 vs Δjitter。拟合出的比例 `k` 和滞后 `lag` 直接给出正确输入：
`measured = k·j(n−lag)`。三种候选分别对应 `k≈0`、`k≈1`、`k≈ratio`。

**本轮结果（EXP-0100，2026-10-29）**：实验做了，用的是比 A/B 更硬的判据（测量见 §11、复核见 §12）：静止相机下量两张
render-size 颜色的亚像素位移 —— `Δj` 最大 0.758 px 时实测 0.06–0.13 px，最干净的一对（`Δj_y = 0.445`）
把 dy 读到 0.000 ⇒ **候选 1 定案：帧没有按它渲染**。产品侧维持 jitter 恒为 0；四档诊断开关
（0 / `j(n)` / `−j(n)` / `j(n−1)`）留在代码里只作诊断，**不要**拿那一轮用户 A/B 去推符号（§12.3）。

## 11. 2026-10-29 双采测量（EXP-0100）：世界帧没有按 jitter 渲染

§6/§7 的三种候选已经判别掉了第一种以外的两种：**帧没有按这个偏移光栅化**。

- 采集：站定不动、对静态贴图，F7 四对（每对两张相隔 ≈131 帧）。两张 `sr_colour_*` 是喂给 DLSS 的
  render-size 颜色（1706x960，fmt26）。两张的 ctx jitter 由 `[vvsr] sr dump … jitter=` 逐张记录。
- 测量：相位相关 + Guizar-Sicairos 1/50 px 上采样 DFT（`_local/tools/jitter_shift.py`），在真实 dump 上
  造已知位移标定到 ±0.01 px。
- 结果（`|Δj|` → 实测位移）：0.758 → 0.063、0.486 → 0.216、0.161 → 0.331、0.462 → **0.028**。
  最干净的一对（五个区域都 0.02 px、相关峰 75k–106k）在 `Δj = 0.46` 时只动了 0.02 px；残差与 `|Δj|` 无序相关，
  较大值随取景区域变化（贴图/物体动画）。
- ⇒ 结论：这个 jitter 是 TAAU **重采样核的相位**，不是世界帧的光栅化偏移。DLSS 侧唯一真实值是 0；
  想要亚像素采样增益必须在渲染侧自己抖相机（`createDeferredRenderingCameras` 已钩），不是喂参问题。

**仍未解释**：产品方 A/B 里 `-j(n)` 与 `j(n-1)` 两档看着也稳、只有 `j(n)` 抖。按本节测量，两档同样注入
~0.37 px 假相位，几何上应与 `j(n)` 同量级；可能是 DLSS 在两档下历史权重不同（观感偏「稳」），或一次观感漏判。
记录在案，**不要**据此推断「符号反了」。

**§8 第 1 条（世界帧是否按它渲染）至此关闭**；§8 第 2 条（NGX 与 Streamline 的约定等价）由本测量顺带变得无关紧要：
既然只能喂 0，两种约定都是 0。
