## 1. 现状核对（2026-10-24，代码逐条核对）

K 把「我们已经有」当成了前提，实际代码里有 6 个旋钮是死的（G §2 仍然成立）：

| 项 | 代码实况 | 证据 |
|---|---|---|
| `Replace=6`（TRP Ratio） | 合成只在 `replace == 5` 时调用，mode 4 算出来却走不到 → 选了也不上屏 | `D3D12Bridge.cpp` 2440 / 2462 |
| `SkinStructureStrength` | 写死 `1.0f` | 同上 2271 |
| 网络预设 | 创建时写死 `0` | 同上 1672 |
| 输入域（原始 HDR） | `useEncoded` 恒真 | 同上 2160 |
| NR 热键（开/关、重置） | 只有面板热键 | `ui/InputGuard.h`、`ui/Overlay.cpp` |
| 参数回读 | 诊断页只有 GPU 中位数/错误码 | `ui/Menu.cpp` 741 |

K §3.4 的 8 项（①输入缩放、②分屏对比、③分阶段计时、④隔帧、⑤自适应曝光、⑥质量修正、
⑦稳态网格、⑧运行时选择）在代码里**都不存在**。

**关键依据（让 ① 变便宜）**：TRP 0.5.3 的 `FeatureContract` 把 feature 尺寸与 guide 尺寸分开，
`NeuralRenderingFeatureSession::RecordEvaluation` 每次求值都把 `Color/Output/Backbuffer` 的 subrect
设成 **feature/work 尺寸**、`Depth/MVec` 设成全分辨率 guide 尺寸，`MV.Scale` 不半减；
`SourceDLSSGNeuralRendering.cpp` 在 `inputScale < 1` 时先 `Downsample` 出 `workColor_` 再喂 NR，
然后用 `Ratio` kernel 在**全分辨率原始色**上合成。⇒ 「小 feature + 全分辨率 guide + 低分辨率色 +
Ratio 合成」是 310.x 运行时上已验证的路径，不需要我们猜，也不需要自己降采样深度/MV。

### P1 — 310.9.16 是否接受 `SkinStructureStrength = -1`

- 探针：配置 `sweep=3` → 每个测量窗轮流写 `-1 / 0 / 1`；TEST 构建逐窗 dump
  `nr_dump_wN.bmp`，并在 `[nr]` 行记录写入值 + evaluate 返回码。
- 判据：① 三窗 evaluate 都返回 1；② `-1` 窗的 dump 与 `0` 窗**逐字节不同**（说明哨兵没被忽略）；
  ③ 若 `-1` 窗 dump 与 `1` 窗相同 → 运行时不认 -1（回落为 1），面板提示改为「0–2」。
- **结果（2026-10-24 实机）**：用户反馈「无论怎么调都看不出区别」。TRP 把这个参数和它的
  **自动皮肤遮罩**配对（`AutoSkinMask`：Finds skin automatically for Skin structure），而我们的输入
  （`UseAutoMask=0`、无 `ControlMask` 纹理）没有皮肤分类可依据 —— 在 MC 画面上它就是一个空旋钮。
- **处置**：正式版面板不再提供该滑条（不存在假开关）；TEST 构建保留，用 `sweep=3` 可继续对照。
  运行时仍写入默认值 1.0，行为与之前一致。

### P2 — 网络预设 0/1 是否真的换网络

- 探针：`networkPreset` 0 与 1 各跑一次（创建时生效，需重启），记录
  `[nr] CreateFeature` 返回码 + 面板 NR GPU 中位数 + 同地点 dump。
- 判据：① 两次 create 都返回 1；② GPU 中位数或 dump 至少一项有可辨别差异 → 值得暴露；
  否则面板文案写「实测无差别」，保留开关但标注。
- **探针就绪（2026-10-24）**：创建日志现在带 `networkPreset=0/1`，诊断页「本帧实际写入 → 网络预设」可回读。
  判定需要**两次启动**（每次 5 分钟）：0 一次、1 一次，比 NR GPU 中位数 + 分屏观感。
- **实测（2026-10-24 05:00–05:04，PASS）**：同一场景、1485×835、输入 100%、`Replace=5`：
  | 预设 | evaluate 中位数 | NR 总中位数 |
  |---|---|---|
  | 0（默认网络） | **3.18 / 3.47 ms** | 3.28 / 3.58 ms |
  | 1（上一版） | **5.85 / 5.84 ms** | 5.89 / 5.95 ms |

  encode（0.02 ms）、composite（0.06 ms）、引擎 DLSS（1.63–1.71 ms）两侧不变 ⇒ 换的确实是**网络本身**，
  且“上一版”在 evaluate 上慢约 **2.6 ms（+80%）**。
- 结论：开关是真的、值得保留；**默认仍是 0（默认网络）**，面板提示已写明“上一版明显更慢（3.2 → 5.8 ms）”。
- 状态：**已验（PASS）**。

### P4 — 引擎是否每帧重写 `Color`（决定要不要做交还）

- 背景：`docs/D §6.16` 的参数表说 `Color` 只在创建时写一次，而 `D3D12Bridge.cpp` 的合成注释说
  引擎每帧重写。两者不能都对；若引擎不重写，合成会变成「拿上一帧自己的输出当底图」的反馈环。
- 探针：`nrRecord` 比较「参数对象给出的 Color」与 `gDecodedColor`，首次相同时写一行 warn。
- **探针可用性缺陷（2026-10-24，已修）**：TEST 构建的 `NR_DEBUG`/`ND_DEBUG` 行被 logger 默认级别丢弃，
  `latest.log` 里根本没有任何 `[nr]` 调试行（只有一条被误报成 "compile failed" 的 warning）。
  已改为 TEST 下 logger 级别与 flush 都是 Debug；`D3DCompile` 的警告也不再写成"编译失败"。
- **2026-10-24 04:54 实测（PASS）**：整局没有出现 `引擎参数对象的 Color 仍是我方纹理` 这行 warn；
  并且加载帧（w0）里参数对象给出的 `Color` 及其编码副本全是黑的，而我们的解码纹理（`nr2`）有内容
  ⇒ 那一帧参数对象指向的确实是**引擎自己的**资源。结论：**引擎每帧重写 `Color`，合成不会形成反馈环**；
  关闭/卸载时的 `nrRestoreEngineColor` 保留为保险。
- 状态：**已验（PASS）**。

### P5 — `Replace=6` 与 5 的画面差异（决定默认值）

- 探针：同一地点、同参数，`compare=1` 下分别用 5 与 6 各看一次；记录面板 GPU 中位数。
- 判据：若 6 明显更暗/更亮或高光丢失 → 默认保持 5；若观感更好 → 默认改 6（需要用户拍板）。
- **结论（2026-10-24 用户拍板）**：**默认改为 6（TRP Ratio）**。面板的「只求值（0）」入口删除，
  运行时代码也不再有这种模式：**任何不是 5 的值都按 6 处理**，配置不做迁移（用户明确「不需要向后兼容」）；
  增益 Boost 滑条只在 5 模式下出现（默认界面不放无效旋钮）。
- 状态：**已验（用户拍板）**。

### P6 — 小 feature + 全分辨率 guide（输入缩放的前提）

- 依据（不是猜测）：TRP 0.5.3 `NeuralRenderingFeatureSession::RecordEvaluation` 把
  `Color/Output/Backbuffer` 的 subrect 设成 **work 尺寸**、`MVec/Depth` 设成 **render 尺寸**，
  `MV.Scale` 保持 render 尺寸 ⇒ 「小 feature + 全 guide」是 310.x 运行时的既有契约。
- 本机判定（一次实机）：面板「输入分辨率」切 66% 与 50%，各看一次：
  ① 日志出现 `[nr] create：渲染 WxH → 特征 fwxfh（输入 66%）`；
  ② 诊断页「输入缩放」显示 `66% fw x fh`；③ 编码/求值/合成三行计时照常；
  ④ 画面无花屏、无半屏错位；⑤ 分屏对比下右半仍有 NR 效果。
- 失败时会发生什么：日志 warn `输入缩放不可用：…% 的特征创建失败，本次运行回落到 100%`，
  NR 自动以 100% 继续，不会整局失效（fail-safe）。
- 状态：待实机（批 2.1 已实现并部署 TEST）。

### P7 — 自适应曝光是否让室内外 NR 强度一致

- 探针：面板「TRP Ratio 参数」区打开「自适应曝光」（默认关），在室内/室外各看一次分屏对比；
  再把 EV 偏置拖到 +1 / −1。
- 判据：① 开关前后画面整体亮度不应漂移（Ratio 合成按原图重基准）；② 室内场景的 NR 效果强度
  与室外相比更接近；③ +EV 时 NR 的观感更明显、−EV 更弱；④ 关掉开关后与旧版完全一致。
- **结果（2026-10-24 实机）**：用户「看着没啥区别，肉眼难以分辨」，要求先记下来以后再测。
- **为什么可能本来就看不出来（结构性，不是 bug）**：Ratio 合成里 `base = original / white`、
  最后 `outC = result * white`，白点对**最终亮度**基本抵消；真正被改变的是 NR 的输入归一化，
  而 NR 在当前内容上的增量只有 1.5–2.5%（docs/D §6.15），差异很难被眼睛抓住。
- **以后怎么测（可测量，不靠肉眼）**：TEST 构建加一个 1×1 白点纹理回读（staging buffer + map），
  在暗场景/亮场景各采 30 帧，比较白点值与同一静止画面的 dump；判据是「白点随场景变化、
  且同一画面 dump 的 NR 输出差 > 0」。开关保持默认关，文案已写明肉眼差异可能很小。
- 状态：**搁置**，等做上面那个回读探针时一并判定。
