# J. SR 内部分辨率：实现、证据与坑（2026-10-24）

> 本文是 `docs/H-sr-plan.md`、`docs/I-sr-final-plan.md` 的落地记录：结论都有一局游戏 + 日志/反汇编证据。
> 与旧文冲突时以本文为准（旧文的"任意百分比做不了"已被 FrameBuilder 因子表推翻）。

## 1. 最终行为

「超分」页 →「内部分辨率」：跟随引擎 / 33 / 50 / 58 / 66 / 100。

每个比例 = DLSS 的原生质量槽，同时驱动两边：

- **DLSS 输入尺寸**：引擎自己的 optimal-settings 答案（不覆盖 `OutWidth/OutHeight`）；
- **场景渲染矩形**：FrameBuilder 的因子表。

「DLSS 模型（预设）」：驱动默认 / E / F / J / K / L / M，写六个 `DLSS.Hint.Render.Preset.*`（保留
`0x80000000`）。应用时若预设变化，强制一次 feature 重建（ctx 换槽 + 尺寸钉住），不需要换分辨率或重进世界。

**75% 不提供**：DLSS 没有原生槽，借槽 + 覆盖 Out 会被槽位动态范围夹住（见 §4）。
**锐化不提供**：运行时已废弃 `Sharpness`（见 §5）。

## 2. 两个尺寸来源（缺一不可）

| 侧 | 谁决定 | 我们改哪里 |
|---|---|---|
| DLSS 输入 | 引擎 optimal-settings 回调（q 槽） | ctx 的 q（`+0xe806dc`），shim 每帧复制到渲染器 |
| 场景渲染矩形 | FrameBuilder 因子表 | `getUpscalingFactor()` 的 `table[fb+0x57c]` |

`FrameBuilder::getUpscalingFactor()` = **虚表槽 83**（我们自己的调用编译成 `call [rax+0x298]`；
按头文件顺序推的 62 是错的）。RT 下按 `[fb+0x57c]` 查表：

```
[0.5, 0.58, 0.667, 0.3334, 0.75]   // RVA 0xE9776E0（1.26.51.01）
index > 4 或非 RT → 常量 1.0
```

patch 表项（`.rdata` 用 `VirtualProtect` 包一次）→ 场景按该比例渲染。实测 100%：
`[desc] Depth` 从 `1485x836` 变为 `2560x1440`，画面正常（2026-10-23 23:07）。
「跟随引擎」时恢复原表值。

## 3. 两个写入者：ctx 才是权威

- `srDriveFrameContext`（每帧 shim，`ctx+0xe806dc`）是真正到达帧构建器的路径；
- `srDriveEngineRequest`（evaluate，渲染器 `+0x3c56428`）每帧会被 shim 用 ctx 覆盖。

所以任何"强制重建"的 nudge **必须写 ctx**。2026-10-24 实测：先写渲染器 → 66↔75 无效；改 ctx 后生效。

## 4. 槽位与动态范围（为什么只有 33/50/58/66/100）

| 槽 | 比例 | 动态范围（2560×1440 下） | 备注 |
|---|---|---|---|
| 3 | 33.3% | 853×480 .. 853×480 | 固定 |
| 0 | 50% | ~1280×720 .. 2560×1440 | |
| 1 | 58% | 1280×720 .. 2560×1440 | Balanced |
| 2 | 66.7% | 1280×720 .. 2560×1440 | Quality |
| 5 | 100% | 2534×1426 .. 2560×1440 | DLAA |

75% 没有原生槽：借 q=5 会被夹到 2534（变 100%），借 q=3 会被夹到 853；只有 q=1/2 的范围能装 1920，
但 66 已占 q=2、q=1 是 58。行为不稳定，2026-10-23 用户决定不提供。

## 5. 不会变成功能的东西

- **Sharpness**：`nvsdk_ngx_defs.h` 里 `DoSharpening` 已标 `SR_DEPRECATED_SHARPENING`
  （"Sharpness is not supported"）。实测写入 0/0.5/1.0 后回调读数仍是 0.35、画面无变化。
  要锐化只能做后处理 pass（CAS/RCAS）。
- **75%**：见 §4。
- **config 热读**：运行期间 config 只写不读（`config::reload()` 已删除，install 里的重读也删掉）；
  文件改动需重启。

## 6. 模型预设与重建

- `srApplyCreateOverrides` 在 CreateFeature 之前写六个 `DLSS.Hint.Render.Preset.*`（保留 `0x80000000`）；
  **0 也写**，否则参数对象复用会让"驱动默认"保留上一次的 K/L/M。
- 预设只在 CreateFeature 读，所以需要一次 feature 重建：
  - `srRequestFeatureRebuild()` 记下当前渲染尺寸；
  - phase 1 用另一个质量槽（写 ctx），phase 2 回到映射槽；
  - 重建期间 sizing 回调把 `OutWidth/OutHeight` 与动态范围钉在记录的尺寸，
    否则临时槽的动态范围会夹住它（q=3→853，q=5→2534）；
  - 「跟随引擎」也支持：基准 q 用 ctx 里的值。
- 只读区会短暂看到临时槽（已加 ~90 帧读数保持，仍偶发）；计划直接删掉只读区。

## 7. CreateFeature 的调用路径（为直接调用留档）

栈（2026-10-24）：

```
exe+dfc7102   ← sizing 0xdfc6c00 + 0x502
exe+dfb606a   ← 0xdfb5ff0 + 0x7a
exe+dfc545b   ← shim 0xdfc53c0 + 0x9b
exe+b725025 … 游戏侧
```

sizing 入口先比较 active/requested mode、factor、feature handle、display size；只有状态变化或 handle 为空
才会走到 +0x502 的 CreateFeature（`0x14e412d30`）。因此直接调用 sizing 而不改状态不会重建——nudge 是必要的。

## 9. 批 S1：RCAS 锐化（已实现并部署；**实机验收推迟到下次进游戏**）

实现位置：`src/neurodragon/sr/SrSharpening.{h,cpp}`（独立编译单元，只 include `<d3d12.h>`），
由 probe 的 evaluate detour 在**引擎 `EvaluateFeature` 返回 1 之后**调用（`RenderProbe.cpp`）。

**落点**：DLSS 之后、引擎调色与 UI 合成之前，所以 HUD 与文字不会被锐化；与 TRP 的
`DLSSBackend::Evaluate` 同一语义位置。

**为什么不能直抄 TRP**：引擎 `Output` 是**线性 HDR**（`DLSS.Feature.Create.Flags=3 = IsHDR|MVLowRes`，
Color 峰值实测 ~69；调色在 SR 之后），而 RCAS 的 clamp 求解只对 [0,1] 成立：
`hitMax=(1−maxRGB)/(4·minRGB−4)`，当「有通道 >1、有通道 <1」时为正 → `lobe` 被夹到 0 →
这些像素完全不锐化（直抄会得到「暗部锐、亮部不锐」的边界伪影）。实现先在 Reinhard 编码域
（`x/(1+x)`，与 NR 编码同一条曲线）锐化，再解回线性。

**资源与状态**：引擎 `Output` 只做 `ALL → COPY_SOURCE → COPY_DEST → ALL` 的往返（TEST 的
`out_after` dump 已在同一资源上用同一条往返），不进入 UAV：
`Output → 私有 A`，RCAS 读 A 写私有 B，`B → Output`。私有纹理对随 `Output` 的尺寸/格式重建，
但要求新尺寸连续 12 帧稳定（拖动窗口期间跳过锐化），被替换的纹理 120 帧后释放。

**第一次实机（2026-10-24 04:30）与修正**：

- `锐化前后 dump：before max=64.38` —— **确认 `Output` 是线性 HDR**（峰值 64）。
- 同帧 BMP 差分：mean |Δ| = **0.38/255**、p99 = 4、只有 11% 像素变化 >1/255 —— 在已经
  很锐的 DLSS transformer 输出上「几乎看不出来」（用户实机反馈一致）。原因不是链路没生效，
  而是 RCAS 的 lobe 上限只有 −0.1875，乘 0.672 后增量太小。
- 修正：lobe 用满量程，**强度改为放大 RCAS 增量 0–4 倍**（编码/感知域内），默认 0.672 ≈ 2.7 倍，
  约等于旧版的 4 倍；`dump` 日志同时打印倍率。1.0 是 4 倍满量程 RCAS，可能出现白边。
- 另加**分屏对比**（`sr.compare` / `sr.compareSplit`）：左半原图、右半锐化，中间 2 像素黑线。
  一帧之内左右相邻，是手机远控/小屏上唯一能确认效果的判据；默认为关，只做诊断用。
  离线模拟（用实机 dump 的 8 位图反推线性值，先验证旧版能复现实测 0.38，再比较变体）：
  默认 2.7 倍时 mean |Δ| ≈ 2.4/255、p99 ≈ 27，是旧版的约 6 倍。
  **2026-10-24 已删除**：分屏只保留「神经渲染」页判断 NR 的那一个（TRP 也只有一个 Compare，
  放在 NR resolve；两个都开会出现两条缝、四段画面）。锐化的 A/B 改为整帧开关；上面这些数字
  是当时用分屏测出来的，保留作历史。

**判定（一次实机，写在这里是为了先有判据再跑）**：

1. 面板「超分 → 锐化」打开并应用 → 日志 `[sr] RCAS 锐化已启用`，画面边缘/纹理清晰度变化，
   HUD 与文字不变；
2. 关闭（或强度拖到 0）→ 日志 `[sr] RCAS 锐化已关闭`，画面与打开前一致；
3. 「超分」页回读：锐化帧数递增，「锐化 GPU」出现中位数（预期 0.1–0.3 ms）；
4. 锐化每累计 120 帧自动写一对 dump（**每次强度变化后重新计时**）：
   `dump/sharp_before_<强度>.bmp` / `sharp_after_<强度>.bmp`（强度取千分位，如
   `sharp_after_672.bmp`、`sharp_after_1000.bmp`），日志给两者 max——`max ≫ 1` 即确认线性
   HDR 域；两张图应只在边缘不同。旧版只在整局第 300 帧抓一次，测第二个强度要重启；现在
   一局就能拿 0.672 与 1.0 两组做离线差分。
5. 拖动/缩放窗口约 10 秒：无花屏、无冻结，停下后锐化自动恢复。

**开放问题**：默认 2.7 倍是否偏锐（用户可在 0–1 之间调）；1.0（4 倍满量程）的白边是否可接受；
HDR 高光处的锐化量是否足够；若「Output 的实际状态不是 ALL_SHADER_RESOURCE」，第一次开启会出现
整帧冻结，处置是关闭锐化并把 `COPY_DEST` 往返改为「只做 SRV 读取」的变体（仍不写引擎纹理）。

**验收状态**：2026-10-24 04:30 第一次实机只验到「链路生效、画面正常、窗口缩放不崩」；增量太小的
问题已按上面的修正改掉。**04:50 第二次实机（默认 0.672 / 2.69 倍 + 分屏对比）**：同帧
`sharp_before` / `sharp_after` 对比给出——**左半（未锐化）逐像素 0 变化**、右半 mean |Δ| = 2.01/255、
p99 = 19、30.1% 像素变化 >2，约为旧版（0.38）的 5 倍；用户反馈「似乎有点区别」。分屏线是精确
2 像素纯黑（列 1280–1281）。**1.0（4 倍）还没测**（用户两次 F2 之间镜头动了，两张图不能作 A/B）
——2026-10-24 17:39 已补测，见下。

**2026-10-24 17:39 第三次实机（按强度分别 dump，整帧开关）**：

| 强度 | before max / mean / >1 | after max / mean / >1 |
|---|---|---|
| 0.672（2.69 倍） | 48.4 / 0.216 / 4.00% | **199.0** / 0.312 / 4.07% |
| 1.000（4.00 倍） | 40.0 / 0.213 / 3.94% | **199.0** / 0.530 / 4.09% |
| 0.673 | 41.9 / 0.204 / 3.83% | **199.0** / 0.295 / 3.89% |

（数值取自日志的 `[dump] sharp_*` 行；BMP 文件本身在 `mods/NeuroDragon/dump/` 里没找到，
该目录只剩同会话后段的 `color_dump` / `output_dump`，不影响上面的统计。）

三点结论：

1. `after max` 三次都是 199.0 —— 那是 `DecodeReinhard` 的 `y ≤ 0.995` 上限（199 = 0.995/0.005）。
   说明高光边缘被 RCAS 推到 Reinhard 域顶端、再解回线性就是原值的数倍。钳制在保护画面不炸，
   但**高光边缘确实有过冲**，1.0 时最明显。
2. 线性均值上升 44%（0.672）/ 149%（1.0）：在编码域（Reinhard）里锐化等于先放大方差再过一条
   凸函数解码，Jensen 偏差把亮部整体抬高；引擎后面的调色/色调映射会压掉一部分，所以观感上的
   亮化远小于这些数字，但「1.0 明显比 0.672 亮」是真的。
3. 判据：0.672 可留作默认，**1.0 不适合做默认**。要压高光过冲，可做「解回线性后夹到 3×3 邻域
   最大值」的无过冲变体（少一点脆度、没有光晕），属可选打磨，不排期。

## 10. 批 S2：成品帧截图（已实现并部署，待实机）

TRP 0.5.3 的做法是钩住 Skyrim 自己的截图保存、再用成品帧覆盖文件；Bedrock 没有这样的函数可钩，
所以等价物是「自己按一个键、在 Present 里抓当前后缓冲」。实现：`src/neurodragon/ui/Screenshot.{h,cpp}`
（D3D11 + WIC，独立编译单元），由 `Overlay` 在 **drawFrame 之前**调用。

- **时机**：Present 钩子里、画我们的面板之前 —— 所以文件是「屏幕所见」：DLSS/NR 之后的成品帧、
  含 HUD、**不含面板**、输出分辨率。
- **键**：`ui.screenshotKey`（默认 `VK_F2` = 0x71；Bedrock 不用这个键），面板开/关都生效，
  按键会被吞掉不再传给游戏；「高级」页的「截图键」按钮可直接改键（与面板键/NR 键同一个捕获
  机制，改完点「应用」）。
- **落盘**：`<version>/screenshots/YYYYMMDD-HHMMSS-mmm-N.png`（**游戏根目录**，与 `mods/`、
  `logs/` 同级，不是 mod 目录里），日志一行 `[shot] 已排队 …` 与 `[shot] 已写入 …`。
- **实现细节**：`CreateWrappedResource` 之后 `AcquireWrappedResources` → `CopyResource` 到
  staging → `Flush`（11on12 的命令在 Flush 时提交，Map 才能等到数据）→ Map → 转 BGRA8 →
  WIC PNG。11on12 的列 pitch 从 `Map` 拿，不自己算。格式支持 B8G8R8A8 / R8G8B8A8 /
  R10G10B10A2 / R16G16B16A16_FLOAT（后者按 Reinhard+gamma 编码，与 dump 同曲线）。
- **反馈**：按下后**聊天栏**出现一行「截图已保存：<绝对路径>」/「截图失败（见日志）」——第一次
  实机（04:50）按键完全没有反馈，用户不知道有没有截上；随后补的底部 2.2 s ImGui toast 又被指
  「太不明显」，2026-10-24 改走原生聊天：`ui::notice::chat`（`GameNotice.cpp`）把文本投给客户端
  线程，再调 `ClientInstance::getGuiData()->displayClientMessage`——纯客户端消息、不发包、不经过
  聊天过滤。路径**必须**是绝对路径：`getModDir()` 给的是相对的（旧日志 `./mods/…`），所以
  `Screenshot.cpp::makePath` 现在自己 `std::filesystem::absolute`，日志与聊天拿到同一串。
  日志仍是两行：`[shot] 已排队 …`（读回+转换耗时）与 `[shot] 已写入 …`（后台编码耗时）。
- **代价**：第一次实机整条链路在 Present 线程上同步跑，**395 ms/张**（可见卡顿）。现在 PNG 编码
  移到单独线程（`CreateThread`，卸载时 join），Present 线程只剩读回 + 转 BGRA；实测新数值待记。
- **实测（04:50）**：两张 PNG 都是 2560×1440、格式 28（`R8G8B8A8_UNORM`）、5.7–5.9 MB、
  含 HUD、不含面板、颜色正确（RGBA→BGRA 交换正确）。

**判据（与 §9 一起、下次进游戏一次测完）**：

1. 按 `F2` → 日志出现 `[shot] 已保存 <路径>`，文件存在且是 PNG；
2. 图内容 = 屏幕所见（含 HUD、**不含**面板）；面板开着按 F2 也不能拍到面板；
